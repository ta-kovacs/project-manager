# Project Manager

A REST API for managing projects and their documents. Users register and log in, create projects (and
become their owner), attach PDF and DOCX documents, and share projects with other users as participants,
either by inviting them by username or by emailing a join link. The requirements are in `TASK.md`. When
the code deliberately differs from it, a comment says so (search for `TASK.md`).

## Stack

- Python 3.12+ (developed and deployed on 3.14), FastAPI, Pydantic v2
- PostgreSQL 17, accessed either through SQLAlchemy 2 ORM models or with hand-written SQL on psycopg (no
  ORM, no SQLAlchemy); Alembic migrations
- AWS: S3 (document files), SES (share emails), SSM Parameter Store (secrets), Lambda (storage usage),
  ECR + EC2 (deployment)
- Docker / Docker Compose, GitHub Actions
- Packaged with `pyproject.toml` (hatchling); tox, pytest (+ moto for AWS), ruff for linting and formatting

## Layout

```
app/
  main.py            FastAPI app; includes the routers
  config.py          every setting, read from environment variables, with local-development defaults
  dependencies.py    get_current_user (JWT) and require_internal_token (Lambda -> API)
  security.py        password hashing (Argon2), JWT access tokens, signed share-link tokens
  storage.py         document file storage: S3Storage (deployed) / LocalStorage (dev, tests)
  mailer.py          email: SesMailer (deployed) / ConsoleMailer (dev)
  routes/            HTTP layer: auth, projects (incl. invite/share/join), documents, internal
  services/          business rules and permission checks; raise domain exceptions; commit
  db/                everything that talks to the database:
    interface.py     the Database protocol (users/projects/documents repositories + commit/rollback)
    records.py       the frozen records repositories return (User, Project, Membership, Document, ...)
    engine.py        engine and get_db, which picks the backend from DATABASE_ACCESS
    orm/             backend on SQLAlchemy ORM models (orm/models/: what Alembic is generated from)
    sql/             backend without the ORM: hand-written SQL on psycopg (PostgreSQL only), schema.sql
  schemas/           Pydantic request/response models
lambdas/storage_usage/handler.py   S3-triggered Lambda: measures each project's storage, reports it to the API
alembic/             migrations (alembic/versions/ are autogenerated)
tests/
  unit/              modules tested directly (security, storage, mailer, the Lambda, both database
                     backends, schema.sql vs the ORM models)
  api/<area>/        one module per endpoint, through the HTTP API (auth, projects, documents, sharing)
  fixtures/<area>.py fixtures, registered for the whole suite in tests/conftest.py (pytest_plugins)
.github/workflows/ci.yml, .github/scripts/deploy-ec2.sh   CI/CD and the EC2 deploy over SSM
docker-compose.yaml (local), docker-compose.prod.yaml (EC2)
```

## How the code fits together

- **Layers:** routes → services → `Database` (app/db/interface.py) → ORM or SQL backend. Routes only
  translate: they call a service and map its exceptions to HTTP errors
  (`except project_service.ProjectNotFoundError: raise ... from None`). Permission checks live in the
  services, which also commit: repositories never do.
- **Two database backends, one behaviour.** `DATABASE_ACCESS=orm|sql` picks `app/db/orm` or `app/db/sql`.
  Both return the records in `app/db/records.py`, never ORM objects, and must behave identically: a
  change to the interface means changing both, plus `tests/unit/test_database.py`.
- **Permissions:** the JWT only identifies the user. Owner/participant roles (`project_users.role`) are looked
  up in the database on every request. A project or document the caller can't access is a `404`, never a
  `403`, so its existence isn't revealed. `403` means "you're a member, but this is owner-only" (delete
  project or document, invite, share).
- **Every endpoint needs `Depends(get_current_user)`**, except `POST /auth`, `POST /login` and `GET /health`.
  `tests/api/test_route_protection.py` fails for any new endpoint that forgets it. Internal endpoints use
  `require_internal_token` instead.
- **Storage and mail are swappable dependencies** (`get_storage`, `get_mailer`) behind a `Protocol`. Routes
  never touch boto3. Document files must live in S3 when deployed; local disk is only for development
  and tests.
- **Storage limit:** `projects.storage_used_bytes` is a denormalized total. The API adjusts it on upload,
  replace and delete with a single conditional `UPDATE`, and the Lambda overwrites it with what S3 really
  holds (newest `measured_at` wins).
- **Settings** are module-level names in `app/config.py`, imported by name where they're used. To change
  one in a test, monkeypatch the module that uses it (see the `max_document_size` fixture).
- **Responses** are JSON with Pydantic response models and specific status codes (201 create, 204 delete,
  401/403/404/409/413/415/422 as appropriate). File downloads are the only non-JSON responses.

## Commands

Use the project virtualenv (`.venv`, Python 3.14); the system Python may be older.

```bash
pip install -e . --group dev            # app (editable) + test, lint and build tools
docker compose up -d db                 # Postgres on localhost:5433
alembic upgrade head
uvicorn app.main:app --reload           # http://localhost:8000/docs

pytest tests/api/documents              # tests for one area (see "Testing")
pytest                                  # full suite
ruff check . && ruff format --check .   # what CI's lint job runs; `ruff check --fix .` / `ruff format .` fix
tox -e py314                            # the suite against the installed package, as CI runs it
python -m build                         # sdist + wheel in dist/
```

Dependencies live only in `pyproject.toml`: runtime ones in `[project.dependencies]`, pinned exactly, and
development tools in `[dependency-groups]` (`test`, `lint`, `tools`, `dev`). The wheel contains only `app/`,
so new code must live under `app/` (or be added to `[tool.hatch.build.targets.wheel]`) to reach the image.

Schema change: change the ORM models, then `alembic revision --autogenerate -m "..."` and review the
result, and make the same change in `app/db/sql/schema.sql` (`tests/unit/test_schema.py` fails until
they match). Never edit a migration that has been merged. Keep `import app.db.orm.models` at the top of
`alembic/env.py`: without it autogenerate sees no tables and generates a migration that drops everything.

## Testing

- `TEST_DATABASE_ACCESS=sql` runs the app on the SQL backend (default `orm`); CI runs both. The SQL
  backend needs PostgreSQL, so on the default SQLite database its tests (and the schema check) are
  skipped; locally, point `TEST_DATABASE_URL` at a throwaway Postgres database to run them. Tests set up
  and check data through the `db` fixture (the same `Database` interface), `count_rows` and `run_sql`,
  never through ORM models, so they work with either backend.
- Locally the suite uses in-memory SQLite and local-disk storage. `TEST_DATABASE_URL` points it at
  Postgres and `TEST_STORAGE_BACKEND=s3` switches to a moto-mocked bucket. CI runs it on Postgres with
  both storage backends.
- Tests go through the API with the caller fixtures (`create_project`, `upload_documents`, ...). Each takes
  the default user's `auth` and accepts overrides; `auth=None` sends no credentials. State a test doesn't
  test is inserted directly (`make_document`, `participant_auth`) rather than set up through other
  endpoints.
- New fixtures go in `tests/fixtures/<area>.py`; a new fixture module must be added to `pytest_plugins` in
  `tests/conftest.py`.

**When to run tests: don't run the full suite after every commit.** It takes several minutes. While
working, run the tests for the area you changed (`pytest tests/api/documents`, a single module, or `-k`).
Run the full suite once, when the branch's work is done and before it's pushed. When splitting finished
work into commits, an import check (`python -c "import app.main"`) or the affected area's tests are enough
for the intermediate commits. CI runs everything on every pull request.

## Branching

- Every piece of work gets its own branch, named `feature/<topic>` (functionality), `ci/<topic>` or
  `chore/<topic>` (tooling, setup, docs). Never commit to `main` directly.
- Branches are merged into `main` through pull requests (merge commits). If the previous branch isn't
  merged yet, branch from it rather than from `main`, and mention that the new branch is stacked on it.
- Don't push, open pull requests or merge unless asked.

## Commits

- Conventional Commits with an area scope: `type(scope): summary`, e.g.
  `feat(documents): limit how much storage each project's documents use`.
  - Types: `feat`, `fix`, `test`, `refactor`, `style`, `docs`, `ci`, `build`, `chore`.
  - Scopes are areas: `auth`, `projects`, `documents`, `sharing`, `storage-usage`, `models`, `db`,
    `deploy`, `lint`. Leave out the scope when a change spans many areas.
- Split work into small, reviewable steps: each feature commit is followed by its own `test(...)` commit,
  and CI/deploy and README changes go in separate commits at the end. Every commit should leave the app
  importable.
- The summary is imperative and lower-case, with no period. The body explains what changed and why,
  wrapped at about 72 characters.

## Gotchas

- Secrets never go in the repository. Production reads them from SSM (`/project-manager/postgres-password`,
  `share-secret-key`, `jwt-secret-key`, `internal-api-token`). A new required SSM parameter must exist
  before the branch that needs it is deployed.
- Deploys run from `main` only: the image goes to ECR, then the EC2 host runs `alembic upgrade head` and
  restarts the app, then the Lambda's code is updated.
